00一分钟版本

一个 HAP、一个进程、三层语言、一条 TCP。ArkTS 画界面，JavaScript 干活，C++ 引擎跑 JavaScript； 三者不是三个进程，是同一个进程里的三层，中间只隔一条回环 socket。

为什么必须同进程：鸿蒙禁 fork/exec，spawn('node') 这条路根本不存在。 出局的只是「宿主 spawn dsh」这一种形态，不是 dsh 本身。

怪癖

process.cwd() 是 /，process.execPath 是 /system/bin/appspawn， os.cpus() 长度为 0。依赖这三者的库会静默出错，所以 HOME / TMPDIR 由宿主显式注入，沙箱根用会话 cwd 而不是进程 cwd。

诊断三件套：node.log（原生桥写的，含 env dump）、 dsh-home/bridge-status.json（state / profile / port / pid / node / wasm）、 dsh-home/bridge.log（bootstrap 自己的日志）。手机上没终端，这三份文件就是全部证据。

02宿主适配层：三段，职责不重叠

① ArkTS 侧编排 NodeHost.ets:58

六步固定顺序：没有 key 直接失败 → 解包载荷 → 备目录 → 写 key 文件 → 投递 Node（九个环境变量）→ 连桥 + 握手。 没有 key 就提前失败是刻意的：不在没有凭据的情况下白跑一遍解包。

② 载荷物化 Payload.ets:21

rawfile 里的 zip 不可寻址，Node 无法从中 require。所以分 1MiB 块复制进沙箱再 zlib.decompressFile；归档长度当幂等戳（payload.stamp）， 载荷一更新自动重解，没变就零成本跳过。

③ Node 侧引导 bootstrap.cjs:804

main() 铺十个垫片，顺序不能乱——因为 ESM 的具名导入是首次 import 时的快照， 晚一步补丁就落不到 import { link } from 'node:fs/promises' 上。

密钥不走 env

原生桥启动时会把子进程环境 dump 进 node.log。所以 key 写成 dsh-home/.api-key（0600），只传路径 DSH_KEY_FILE， 由 bootstrap 在日志写完之后才赋给 process.env.DEEPSEEK_API_KEY。 新增任何敏感变量都沿用这个模式。

03协议层：一条桥，两个 profile

传输只有一种：127.0.0.1:4517 TCP，一行一帧 JSON-RPC 2.0。 bootstrap 把 socket 管进进程级的 PassThrough，再用 Object.defineProperty 覆盖 process.stdin/stdout （Node 24 里这俩是 getter-only，直接赋值会抛）。两个刻意设计：

  • 首次连入才 boot dsh —— 保证 dsh 的 stdout 从第一帧起就有接收方，不会丢初始化输出。
  • socket 断开只 pause 不 end —— stdin EOF 会被 dsh 当成 shutdown，UI 掉线不能杀运行时。
两个 profile 的差异（桥本身与 profile 无关）
SDKACP
方法 5 请求：initialize / session/prompt / session/resume / session/working-directory/set / shutdown 9 方法：initialize + session/new|list|resume|close|prompt|cancel|set_config_option
通知 4 个；session.event 是全运行时事件流，客户端按 sessionId 过滤 session/update 五种 chunk
审批 无通道 服务端发起 session/request_permission，两键 allow-once / reject-once，fail-closed
流式 无（一步结束才发 assistant/message） 有（agent_message_chunk / agent_thought_chunk）
sessionId 客户端生成，未知 id 懒创建 服务端生成
取消 无 session/cancel 是通知，带 id 发会 Method not found

踩出来的硬契约

以下每一条都是实测结论，写进注释就是契约本身（AcpProtocol.ets 文件头）：

  • 事件信封 {type, seq, time, data}，字段在 data 下；读扁平结构 = 对话永远空列表。
  • 帧必须带 "jsonrpc":"2.0"，缺失时预校验直接回 -32600，到不了方法分发。
  • set_config_option 的 model value 是 JSON 数组字符串；响应里的 configOptions 是新的权威列表，而且选项集会收缩——默认模型一旦切走，该会话切不回来。
  • session/prompt 在 inflight 时被拒 ⇒ ACP 没有 steering。「插话」只能是排队，或先 cancel 再发。
  • 完全不答审批 ⇒ 那一轮无限挂起，不是工具失败；服务端不会自动放行。
  • 方法名全部 snake_case，按 ACP 规范猜 camelCase 一律 Method not found。
断线重连的语义陷阱

断线时正在跑的那一轮，服务端继续跑，session/update 也会投给新连接；但 原 session/prompt 的响应永久丢失，且 update 帧里没有 turn id， 客户端无从判断它何时结束。所以恢复必须走重置语义： initialize → session/close 掐掉孤儿轮 → session/resume → 把那条消息标为「已中断」让用户决定是否重发。退避是 120s 起、翻倍、上限 300s、六次。

04沙箱：四层，而且没有一层是内核级进程沙箱

这是最容易被误解的一块。设备上真正拦住模型的不是「沙箱」这个词，而是文件路径收口 + 审批门； 内核级隔离那一层，在这里是缺席的。

  1. L0 系统应用沙箱内核级

    每个 App 一个 uid，只能碰 /data/storage/el2/base/haps/entry/files/…。这是唯一真正的安全边界。

  2. L1 目录授权系统授权

    用户用系统选择器挑目录，FILE_ACCESS_PERSIST + fileShare.activatePermission() 把授权持久化并暴露真实路径 /storage/Users/currentUser/…，Node 用普通 POSIX 调用就能读写； 父目录和兄弟目录仍 EPERM。

  3. L2 dsh 文件沙箱进程内策略

    dsh-fs-sandbox 只栅住变更（write / edit / patch / delete / move），读一律放行。 workspace-write 要求目标 canonicalize 到会话 cwd 或平台临时目录， 否则抛 FS_SANDBOX_DENIED。

  4. L3 审批策略

    ask / never 两档，由权限预设捆绑；ACP 下是 session/request_permission， 答错或空应答一律 fail-closed。SDK profile 下没有这条通道。

The fence is a policy check in TRUSTED code over a MODEL-CONTROLLED path, NOT a kernel boundary. This is containment, not a security boundary.

dsh-fs-sandbox · src/index.ts

那 ctx.sandbox（进程沙箱）呢？dsh-sandbox-local 在设备上必然 SANDBOX_UNAVAILABLE——它的后端是 bwrap / landlock-run / Seatbelt / Windows ACL， 每一个都要 spawn。这也正好和「bash 整族被禁」自洽：没有 shell，就没有需要内核沙箱去关的东西。

权限三档：沙箱与审批捆绑，启动期固化
档位文件变更审批真机表现
read-only 全部拒绝 ask 裸写先被沙箱拒（无审批请求）；带 sandbox_permissions 重试才触发审批
workspace-write（默认） 工作区内直写 ask 越区才问
danger-full-access 不栅 never 全放行、零审批

档位由 DSH_PERMISSION_MODE 在启动期固化，会话创建时写进 permission/preset、sandbox/mode、approval/policy 三条事件 ⇒ 切档要重启 App，且只影响新会话。

07口径冲突：三处文档与代码对不上

这一节不是风格问题，是这轮读代码发现的实际问题。按「代码为准」列出，并给出建议。

① 默认 profile：代码是 SDK，两份文档说 ACP

AppConfig.ets:51 默认 'sdk'， 设置页按钮也写「SDK（默认）」；而 API-AND-SEQUENCE.md §2.1 写「ACP（默认路径）」，AGENTS.md §9 也注「实际默认 ACP」。

以代码为准：全新安装跑的是 SDK。

② 这不只是口径问题，是能力问题

bootstrap.cjs:743 的 installProfileTemplate() 只在 PROFILE === 'acp' | 'ohos' 时才装模板。所以 SDK 默认路径下整套 ohos 插件都不挂：

  • 纯 JS 搜索不挂 ⇒ stock tool-fs-search 走 spawn ripgrep ⇒ glob / grep 在默认配置下是坏的；
  • credentials-live 不挂 ⇒ 改密钥要重启（代码里 toast 就是这么分叉的）；
  • boot-report 不挂 ⇒ 手机上没有任何工具表自检；
  • time-context 不挂 ⇒ 模型不知道「今天」；
  • 无审批通道、无流式。

换句话说：「默认」是兼容历史的降级路径。 2026-11-20 已加首启引导：第一次启动问一次「用 ACP（推荐）/ 用 SDK」， 答案决定当次启动、不用重启；默认值本身没翻——ACP 的 sessionId 与 SDK 不通用，全量切换会让老会话的上下文失效。

③ 小口径漂移

工具数曾同时存在 21 与 25 两个口径（21 是 0.2.1 的数），载荷升到 0.2.2-rc.5 后已统一为 25；ARCHITECTURE.md 已在 2026-11-20 重写 （不再把 SDK 写成主路径，补上了 ohos profile 与审批）。 仍然漂着的是 BOOT.md 的行号（bootstrap 现在 850 行， main() 在 804 不是 789）——读它时按函数名找，别按行号。

建议：改代码默认值的同时，同 commit 修这三份文档，避免下一轮 agent 又被旧口径带偏。

本文与旧文档的关系

权威文本：docs/ARCHITECTURE.md（本页是它的排版版，改内容先改那里）。 本文是「四层 + 取舍」的一页综述，不替代 BOOT.md 的逐行走读、 SPIKE-ACP.md 的 ACP 实测矩阵、 GAP-ANALYSIS.md 的能力差距清单。 三者的结论冲突时，以本文标注的代码行号为准。 想知道这些设计里哪些是硬啃下来的、代价是什么，看 突破清单（排版版 breakthroughs.html）。
