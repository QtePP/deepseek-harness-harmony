00什么才算突破

「突破」这个词很容易通货膨胀。所以先定尺子——四条同时成立才算，缺一条就降级成苦工：

四条判据
判据为什么它把大部分工作筛掉
平台明确说不行不是「麻烦」，是文档或权限模型直接判死：禁 fork、无 WASM、patch 不能加行
没有现成方案可抄要么逆向机制，要么自己写；照文档做能成的事不算
真机闭环过「理论上可行」不算，得在设备上跑出结果
用户能感知模型能搜到文件、能改文件、能流式回答——不是内部重构

按这个尺子，六件够格。它们的共同点是：没有一件是「绕过限制」，每一件都是「换一条实现路径」—— 限制还在，只是不再是瓶颈。

01六件平台突破

平台说「不行」的六件事，逐一变成了「行」
平台限制常识结论实际做到换的路径
禁 fork/exec 跑不了 Node 运行时 同进程跑起完整 dsh dlopen libnode.so + node::Start
没有子进程 stdio ACP 用不了 进程内 ACP，零 spawn 回环 TCP → PassThrough → 覆盖 stdio
jitless ⇒ 无 WASM fetch 全废 有 HTTP，且是干净的那种 整族替换 + ESM resolve hook
patch 只能改/禁已有行 平台插件装不进去 6 个自研插件真实挂载 自定义 profile + bundle insert
禁硬链接 + 非 POSIX 挂载 原子写、文件工具必炸 write / edit / patch 全部可用 三条降级链，打在 ESM 快照之前
无终端 设备上是黑盒 有可观测性 boot-report + 三份日志 + 诊断面板

01同进程 Node：地基，但不是我们一个人铺的

平台说
禁 fork/exec，不能 spawn('node')。
我们做
把 Node 作为本进程的一个 detached pthread 拉起来，跑真 dsh。
证据
bridge-status.json 里 node=24.2.0、wasm=false；真机启动 0 个未激活行。
代价
崩溃即终态（node::Start 每进程一次）、无进程隔离、必须劫持 stdio、载荷 240MB。

诚实归属：引擎入进程是第三方 @fellow99/node-bridge 做的。我们的突破是「让 dsh 在这个引擎上活下来」—— --jitless --expose-internals 的取舍、九个环境变量的接线、密钥不走 env 而走 0600 文件（原生桥会把 env dump 进日志）， 以及「首次连入才 boot dsh」这个顺序，保证 stdout 从第一帧起就有接收方。

02进程内 ACP：官方文档没给的路

平台说
ACP 是「宿主 spawn 一个子进程，用 stdio 说话」——这条路在鸿蒙上直接死。
我们做
不换协议，换掉「stdio」这个概念本身：socket 进来 → 管道进进程级 PassThrough → dsh 以为自己在读 stdin。
证据
9 个方法 + 流式 + 服务端审批全部真机闭环；还能用 hdc fport 从电脑直接驱动设备端运行时。
代价
桥是单客户端（新连接顶掉旧连接）；断线重连语义得自己扛。

三个细节全是踩出来的：Node 24 里 process.stdin 是 getter-only（直接赋值抛），必须 defineProperty； 流必须是进程级的（每次连接重建会让重连后的运行时读一根孤儿管道）；socket 断开只能 pause 不能 end ——stdin EOF 会被 dsh 当成 shutdown。

03fetch-shim：一次「为什么必须这样」的推导

平台说
jitless ⇒ 没有 WebAssembly ⇒ undici 的 llhttp 起不来 ⇒ fetch 全废。
我们做
整族替换 fetch / Headers / Response / Request / FormData，再挂一个 ESM resolve hook 拦 await import('undici')。
证据
启动即 boot: sdk runtime mounted，0 fatal；旧版本只剩一条良性的 WebAssembly is not defined。
代价
无 WASM 连带：TS 擦除不可用（模型要写纯 JS）、sharp 只能原字节直通。

关键发现：只换 fetch 会崩。因为 dsh 启动期会读全局 Headers，一读就触发 undici 的惰性物化， 而它的 llhttp 是 WASM——崩在启动阶段，日志里只留一条看起来「良性」的 unhandled rejection。这是本项目技术含量最高的单点。

04自定义 profile：把「不能加行」逆向成一套机制

平台说
patch 只能改或禁已有行，不能新增。
我们做
新行只能来自 bundle 的 cordis.patch.yml 顶层 - insert:，且插件包必须写进 bundle 的 dependencies。
证据
5 个插件真实挂载；--dump-config 行命中；真机工具表含 glob/grep 且无 bash。
代价
装配链复杂；升级 dsh 要复核行 id；载荷里残留的同名测试包会遮蔽 profile 内的新版。

价值不在「我们装上了插件」，而在「不 fork dsh 也能给平台加能力」这条路被证明了—— 纯 JS 搜索、in-process PTC、密钥热更新、时间上下文、boot 自检，五件都挂在这条路上。

05三条降级链：每条都只在真机上暴露

平台说
禁硬链接；沙箱只认 app files 根以下；/storage/Users 是 FUSE 语义。
我们做
copyFile(COPYFILE_EXCL) 保排他语义 / 只读 open 目录给空壳 handle / 三条 mount-aware 降级。
证据
会话写得进；内联图片不再报「unable to persist」；绑定用户目录后写文件正常。
代价
每一条都必须「只在这个挂载上容忍、其它一律照抛」——放宽一点就是把错误吞掉。

共同点：都不是功能缺失，而是某个底层 syscall 的语义在这个文件系统上不成立。 这类问题纸面推不出来，只能真机撞。

06无终端 → 可观测性

平台说
手机上没有 shell，出了问题只能猜。
我们做
启动 5 秒后把已注册工具名 + web search/fetch 就绪状态写进 bridge.log。
证据
当场结掉两个悬案：工具表 21 还是 25（是 25，某台机器关了 tool-fs 开关）、「模型说不能搜网」到底是哪种原因。
代价
它只是诊断，不修复任何东西；而且它自己也会过时——升到 rc.5 后真的误报过 search=ambiguous，因为上游把搜索改成按路由偏好选、它还在按「唯一可用」判定。已按规则修好（单测 11 → 20）。

02把黑盒写成契约

这一层不算「平台突破」，但它是别人抄不走的部分：每一条都是真机实测出来的，写进注释就是契约。 最反直觉的四条：

契约按直觉做会怎样
session/cancel 是通知带 id 发（当请求）→ Method not found
set_config_option 的 model value 是 JSON 数组字符串传对象 → 静默不改，没有报错
选项集会收缩缓存旧列表 → 切走默认模型后切不回来，-32602
不答审批 = 无限挂起以为会超时失败 → 实际是整轮卡死，服务端不自动放行
最有价值的一条：协议缺陷 → 产品设计

断线时正在跑的那一轮，客户端无从判断它何时结束：原 session/prompt 的响应随 socket 一起丢了， 而 session/update 帧里没有 turn id。协议给不出答案，只能在产品层解决—— close 掐掉孤儿轮 → resume → 把消息标成「已中断」让用户决定重发。 这条转化比任何一条协议实现都难写。

03用「官方没提供」当设计依据

官方 ACP README 明确写「intentionally exposes only the standard ACP v1 surface」，并点名 cards / plans / titles / todos / terminal views 不在协议里。 这句话别人看是限制，我们看是唯一路径的证明：

  • 待办条 / 目标条 / 上下文小环 / 每轮用量 / 子代理计数——全部从 tool_call 参数反推，零协议改动，冷启动还能从持久化轨迹重建。
  • 密钥热更新——dsh 启动期冻结 env 快照，改 env 永远无效；所以不碰 env，改成监听暂存文件 → credentials.set()，2 秒生效。
  • 图片存相册——用 SaveButton 安全组件换临时媒体权限，而不是申请受限权限（那要过 AGC 审批，还会把普通应用变成受限应用）。
  • 语音——先勘误旧结论（「SDK 不含 CoreSpeechKit」是错的，只看了 openharmony/ets/kits，没看 hms/ets/kits），再做「引擎起不来也不烂」的降级 + 复位入口。

04方法论：把「能不能上设备」变成可本地预演

如果只能带走一件，我选这个。以前「设备上跑不起来」是个黑洞，只能反复刷机猜；现在真机被降级成最后一道闸。

  1. 改 host/只动 bootstrap.cjs、垫片、profile 模板或补丁 YAML。
  2. --dump-config看行 id 是否命中、禁用行是否生效、tools 行的 mode 对不对。
  3. 本地起一次 runtime--profile ohos + 等 boot-report。零警告才算过。
  4. 三段验证载荷单测 + ArkTS 检查 + LocalUnit，一条 scripts/test.sh 跑完。
  5. 最后才装机重打载荷 → build → 签名 → 装。真机只用来确认，不用来发现。

这套顺序救过一次典型的坑：schedule 插件插进去后，本地日志直接给出 pending (waiting for service: sessionController)——当场判定「缺的是宿主服务，不是插件」， 回滚，没浪费一次装机。

配套的是证据纪律：先取证再下结论。语音那条结论错了四天，错在只看了一个目录； 工具数 21 的争论，错在把「用户关了开关」当成「升级回归」。

05什么不算突破

清单的另一半同样重要——这四类工作占了大部分时间，但按判据一条都不够格。

不在清单里，理由各不相同
类别内容为什么不算
苦工 UI 对齐 dsh-go 的十几条：流式、排队、引用、重答、搜索、置顶、归档、多选、分享卡、导出 量很大（15k 行 ArkTS），但没有一条是「平台说不行」
补债 真机缺陷：父手势吞子手势、顶栏落进状态栏、重启丢回复、通知授权时机 是我们自己写出来的 bug，修好只是回到基线
流程债 三次口径漂移：默认 profile、工具数 21/25、ARCHITECTURE.md 过时 已还两项（工具数统一为 25、ARCHITECTURE.md 2026-11-20 重写）；默认 profile 仍未决，且已是产品缺陷
未突破 默认 profile 仍是 sdk，全新安装跑的是降级路径 2026-11-20 加了首启引导（问一次，答案决定当次启动）；默认值本身没翻，因为 ACP 的 sessionId 与 SDK 不通用

06只留三件

如果这个项目只能留下三样东西，按「换来的能力 ÷ 付出的代价」排序：

  1. 1
    进程内 ACP

    它让「协议层」这件事在鸿蒙上重新存在。没有它，后面所有流式、审批、取消、重连都无从谈起。

  2. 2
    fetch-shim 的整族替换

    它不是补丁，是一次对「为什么必须这样」的完整推导——而且推导错一步，应用就崩在启动阶段。

  3. 3
    自定义 profile 的 route-table 机制

    它把「不能 fork dsh」从限制变成了可扩展性：平台差异不再需要改上游源码。

第 4 名留给 boot-report。技术含量不高，但它把整个项目的可调试性抬了一个台阶—— 而可调试性，是这 26 天里唯一让「猜」变成「看」的东西。
