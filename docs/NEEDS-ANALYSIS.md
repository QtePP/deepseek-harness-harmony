# 手机端独有能力 × 需求分析

> 目的：回答「手机端跑 dsh 到底有什么不可替代的价值」，并给出一套可复用的筛选方法。
> 日期：2026-10-27。结论基于本仓库的实际约束（禁 exec、jitless、单 App 沙箱）。

---

## 1. 手机独有能力清单（按「桌面能否替代」分层）

### A. 硬件输入 —— 桌面物理上没有

| 能力 | 典型用途 | 备注 |
|---|---|---|
| 相机 | 拍照、文档扫描、扫码、实时翻译、板书/白板 | 手机最强的内容入口 |
| 麦克风 | 语音速记、会议转写、灵感捕捉 | 配合系统 ASR 可离线 |
| 定位 | 行程记录、票据归档、附近信息 | 隐私敏感，需显式授权 |
| 运动/健康传感器 | 步数、心率、睡眠 → 周报 | Health Kit |
| NFC / 蓝牙 | 门禁、设备配对、标签 | 场景窄 |
| 震动 / 闪光灯 | 任务完成的触觉反馈 | 低成本高感知 |

### B. OS 级集成 —— 桌面有，但形态完全不同

| 能力 | 为什么手机更强 |
|---|---|
| **通知** | 唯一能「主动找到你」的通道；桌面程序不响 |
| **分享面板** | 从任何 App 一键送进来（浏览器、微信、相册），这是手机独有的入口 |
| **剪贴板** | 跨 App 的临时数据流，桌面弱得多 |
| **小组件 / 负一屏** | 零启动成本，看一眼就有 |
| **日历 / 通讯录 / 短信** | 情境数据，且是「真人在用」的那份 |
| **相册 / 文件** | 用户的全部生活资料 |
| **后台任务** | 受限但存在，够跑「夜里整理」 |

### C. 形态与情境 —— 不是能力，是场景优势

- **随手性**：3 秒能开始，桌面要开机、找窗口
- **碎片时间**：等电梯、排队、走路
- **私密性**：数据不出设备（本地优先叙事）
- **离线**：飞机上、地铁里仍可用

### D. 看似能做、实际被平台掐死的（重要）

| 能力 | 现实 |
|---|---|
| 控制其它 App（自动点按、跨 App 操作） | 需要无障碍类能力，鸿蒙上通常要系统级签名 / 特殊授权，普通应用基本拿不到 —— 这条路对我们基本是死的 |
| 长期后台常驻 | 系统会杀，不能当守护进程用 |
| 读其它 App 的数据 | 沙箱隔离，拿不到 |
| 跑外部二进制 / 编译 | 禁 fork/exec |
| 后台读剪贴板 | 受限，通常需用户在前台动作触发 |

> 这一栏比前三栏更重要：**它决定了竞品能做的事我们做不了，别照着抄。**

## 2. 需求分析框架（选一个主用，别混着来）

通用框架有三个，但对这个项目都不够——因为它们不把「技术可得性」当硬约束。

| 框架 | 回答什么 | 局限 |
|---|---|---|
| **JTBD**（情境→任务→路径） | 用户在什么处境下想完成什么 | 不考虑我们做不做得到 |
| **Kano**（基本/期望/兴奋） | 哪类需求能带来满意度跃迁 | 需要真实用户样本 |
| **场景五维**（时间+空间+状态+关系+事件） | 场景切得够不够细 | 容易发散 |

**本项目建议用三维打分**，把技术约束前置：

```
得分 = 手机独有度(0-3) × 使用频次(0-3) × 可实现性(0-3)
```

- **手机独有度**：桌面能不能等价做到？能=0，勉强=1，明显更好=2，只有手机能=3
- **使用频次**：一年几次=0，每月=1，每周=2，每天=3
- **可实现性**：现有 API 直接能做=3，要写不少代码=2，要突破平台限制=0

乘法而不是加法：任一项为 0，整条需求就该砍。

## 3. 候选需求打分

| # | 需求 | 独有度 | 频次 | 可实现 | 分 | 结论 |
|---|---|---|---|---|---|---|
| 1 | **分享/截图进来 → 结构化提取 → 沉淀成卡片** | 3 | 3 | 3 | **27** | 做 |
| 2 | **定时任务 + 系统通知**（日报、跑完提醒） | 3 | 2 | 3 | **18** | 做 |
| 3 | 拍照 → 票据/名片/菜单 → 记账或通讯录 | 3 | 2 | 2 | 12 | 做（依赖 OCR） |
| 4 | 语音速记 → 转写 → 归类 | 3 | 2 | 2 | 12 | 做（依赖 ASR） |
| 5 | 桌面小组件：一句话输入 + 最近结果 | 2 | 3 | 2 | 12 | 做 |
| 6 | 剪贴板历史 → 自动整理 | 3 | 3 | 2 | 18 | 做（注意隐私：只在前台读） |
| 7 | 健康数据周报（Health Kit） | 3 | 1 | 2 | 6 | 缓 |
| 8 | 日历冲突检查 / 自动排期 | 2 | 2 | 2 | 8 | 缓 |
| 9 | 离线文件整理 | 1 | 2 | 3 | 6 | 已有，不投入 |
| 10 | 语音对话（免手） | 2 | 2 | 1 | 4 | 缓 |
| 11 | 多设备接力（手机产出，电脑继续） | 2 | 1 | 1 | 2 | 不做 |
| 12 | 控制其它 App | 3 | 3 | **0** | 0 | **砍**（平台不允许） |
| 13 | 移动 IDE / 终端 / 包管理 | 0 | 2 | 0 | 0 | **砍** |
| 14 | 大屏 BI 看板 | 0 | 1 | 2 | 0 | **砍**（桌面更合适） |
| 15 | 长任务跑完通知 | 3 | 2 | 3 | 18 | 做（成本最低） |

**前三名：#1 分享/截图入口、#2 定时+通知、#15 长任务通知**——它们共同点是：**手机独有、频次高、不需要突破平台限制**。

## 4. 开源案例对照

### 4.1 外部控制型（我们做不了，但要知道）

| 项目 | 做法 | 对鸿蒙 |
|---|---|---|
| **Mobile-Agent**（阿里） | 截屏 → VLM 理解界面 → 决策 → 点按 | 需要无障碍/注入能力，第三方拿不到 |
| **AppAgent**（腾讯） | 探索式学习 App 的 UI 元素，生成操作脚本 | 同上 |
| **AutoDroid**（清华） | 结合 UI 树与 LLM 生成操作 | 同上 |
| **droidrun / Mobilerun** | 设备农场 + agent 批量操作 | 同上 |

共同链路：`截屏/UI树 → 理解 → 决策 → 执行 → 循环`。
**结论：这条赛道在鸿蒙上是死路**，不是技术难度问题，是权限模型问题。别照抄。

但可以借一点：**「状态-动作-校验」的任务分解思路**——它比让模型自由发挥更稳。

### 4.2 本地优先 / 第二大脑型（我们该学的）

| 项目/方向 | 可借鉴点 |
|---|---|
| **Obsidian / Logseq** 类 local-first | 数据主权叙事：用户相信「东西在我机器上」 |
| **second-brain-ai-assistant** 课程（decodingml） | 个人数据 + RAG 的组织方式 |
| **Meetily**（本地会议转写） | 语音 → 转写 → 摘要全本地，对应我们的「语音速记」 |
| **VeloxWaves** 类本地听写 | 隐私作为卖点，而不是功能 |

**结论：活路是「输入 → 结构化 → 沉淀」，而不是「替你操作 App」。**

## 5. 需求分析怎么做（落到每周动作）

方法论再多，不如一个能坚持的动作。建议：

1. **场景日志**（每周 5 条）：记下「我在哪、想干什么、掏出手机做了什么」。
   只记你**真的掏出手机**的那 5 次——没掏手机的说明不需要手机。
2. **反推能力**：每条场景标注用了哪个手机独有能力（相机/通知/分享/定位…）。
   标不出来的，独有度就是 0，直接砍。
3. **每周选一条做成卡片**：用现有 `write` 工具生成一个 HTML 卡片，先在 Web 组件里看效果。
   能在 30 分钟内做出来的，才值得进产品。
4. **月末复核**：哪条卡片你这一周打开过 3 次以上？没打开的，删掉。

这个循环比任何 Kano 问卷都有效——因为样本是你自己，而你自己不会骗自己。

## 6. 一句话结论

**手机端 dsh 的价值不在「能跑代码」，在「能就地接住你随手扔进来的东西，并在合适的时候主动找你」。**
前者桌面完胜，后者只有手机能做。产品边界就画在这句话上。
