# 个人 Agent 与功能卡片：下一步演进方案

> 日期：2026-10-31。基线：`feature/acp`；ACP 客户端已交付，但默认 profile 仍是 `sdk`；
> 载荷 zip ≈225 MB、HAP ≈335 MB；设备端 Node v24.2.0、`--jitless`、禁 fork/exec。
> 本文的判断尽量落在**已有代码与 dsh 0.2.1-rc.4 源码**上；凡属推测的地方会写明。

---

## 0. 结论（先看五条）

1. **下一步不是加工具，是换壳。** 现在的产品是「聊天窗口 + 文件产物」；下一步是
   「Agent 卡片板 + 对话」。前者回答"你问什么"，后者回答"它替你把什么维持住了"。
2. **个人 Agent 不需要新协议。** dsh 已有三块现成地基：`cwd` 决定 workspace、
   `AGENTS.md` 决定人格、`.dsh/skills` 决定能力。**一个 Agent = 一个目录**，
   ACP 的 `session/new` 只要把 `cwd` 指过去，其余全是文件。
3. **功能卡片用声明式 JSON，不让模型生成 HTML。** 一份 CardSpec 三处渲染：
   应用内、桌面卡片、通知。HTML 只留作一次性富产物的逃生舱（现有 ArtifactDock 已支持）。
4. **数字必须由纯 JS 脚本算，模型只写文案。** 热量、配速、保底次数、伤害期望——
   模型心算不可靠，而卡片上的错数字比聊天里的错句子严重得多。
5. **对 Muse 不要在"替你办事"这条轴上竞争。** 跨 App 操作在鸿蒙上被权限模型掐死
   （`docs/NEEDS-ANALYSIS.md` §1.D）。我们的轴是「接住 → 结构化 → 沉淀 → 提醒」；
   Muse 的四件套（Goals / Activity / Approval / Artifacts）我们已有两件，
   缺的两件成本很低。

## 1. 现状盘点：运行时够用，壳不够

| 能力 | 现状 | 差距 |
|---|---|---|
| 对话 / 流式 / 取消 | 已有（ACP 路径） | 默认仍是 SDK，需转正 |
| 审批 | `session/request_permission` + ApprovalSheet | 只在 ACP 路径可用 |
| 文件产物 | `ArtifactDock`：网页 / 图片 / 文本，横向卡条 | **只认文件，不认"状态"** |
| 工具轨迹 | 当前轮的 trace 行 | 没有跨轮、跨会话的活动账本 |
| 目标 | dsh 有 `create_goal` / `update_goal` | **没有 UI 投影**（web 端有，我们没接） |
| 项目 | 命名桶 + 独立 workspace（`filesDir/workspaces/<id>`） | 只是分类，不是 Agent |
| 技能 | dsh 原生：`cwd/.dsh/skills`、`AGENTS.md` | 没有入口、模板、切换 |
| 主动性 | 无 | 无通知、无定时、无桌面卡片 |
| 多 Agent | 单 session 模型 | 无切换器、无身份 |

一句话：**dsh 负责"能干什么"已经够了；我们缺的是"它替你维持了什么"这层界面。**

## 2. 三个转变

### 2.1 从「会话」到「Agent」

现在用户面对的是"新会话"。改成"面对一个 Agent"：

- Agent 有名字、头像、语气、固定职责（饮食教练 / 游戏伙伴 / 周报助手）；
- Agent 的工作区就是它的家：人格、技能、数据、卡片都在里面，**可导出、可备份、可手改**；
- 会话只是它的工作日志，不再是产品的主语。

### 2.2 从「文件产物」到「状态卡片」

文件是"一次任务的输出"；卡片是"一件持续的事的当前状态"。

| | 文件产物 | 状态卡片 |
|---|---|---|
| 生命周期 | 一次任务 | 长期，反复刷新 |
| 内容 | 文档 / 网页 / 图 | 数字、进度、清单、趋势、资讯 |
| 谁更新 | 用户或模型重写 | Agent 每次运行增量更新 |
| 过期语义 | 无 | 有（`generatedAt` / `staleAfter`） |
| 能不能上桌面 | 不能 | 能 |

### 2.3 从「被动问答」到「打开即补齐」

没有云端常驻，就不可能有 Muse 那种"它在替你办事时给你发消息"。本地能做的主动性是：

```
定时提醒（系统通知） → 用户点开 → 前台 catch-up：扫过期卡片 → 跑刷新 → 更新板
```

诚实地说，这是"提醒驱动的主动性"，不是"常驻代理"。但 80% 的个人场景（记一餐、
清体力、看周报）需要的正是"到点提醒 + 打开就有"。

## 3. 架构：Agent Pack + CardSpec + 三处渲染

```
┌─ 表现层（ArkTS）──────────────────────────────────────────────┐
│  Today 卡片板        对话 + 审批        桌面卡片 / 通知        │
│  CardRenderer  ────────────────►  CardRenderer(子集)          │
└──────────────▲───────────────────────────────────────────────┘
               │ 读 CardSpec(layout) + CardData(snapshot)
┌─ 约定层（文件）┴──────────────────────────────────────────────┐
│  workspaces/<agentId>/                                        │
│    agent.json     AGENTS.md     .dsh/skills/                  │
│    cards/*.card.json            data/*.json                   │
└──────────────▲───────────────────────────────────────────────┘
               │ 读写（write / edit / card_publish）
┌─ 运行时（同进程 dsh）─────────────────────────────────────────┐
│  skill 目录 · 工具（fs/web/goal/subagent）· 模型 · 会话日志     │
└───────────────────────────────────────────────────────────────┘
```

### 3.1 为什么 Agent 用「项目」而不是新建一套

`ProjectModel` 已经解决了：命名、独立 workspace、会话归属、切换。把 Agent 做成
"带 `agent.json` 的项目"，可以**零迁移**复用全部现有链路（`session/new` 的 cwd、
`SessionStore` 的索引、`FilesPanel` 的浏览）。

`agent.json`（最小集）：

```json
{
  "schema": 1,
  "id": "diet-coach",
  "name": "饮食教练",
  "emoji": "🥗",
  "accent": "green",
  "home": "today",
  "cards": ["today", "week"],
  "schedule": [
    { "id": "lunch", "at": "12:30", "prompt": "提醒我记录午餐", "notify": true }
  ]
}
```

### 3.2 人格与能力从哪来（已有 seam，不用改 dsh）

| 需求 | 机制 | 证据 |
|---|---|---|
| 人格 / 工作准则 | `<cwd>/AGENTS.md`，首次请求前注入 | `dsh-agent-instructions`，预算 65536 B |
| 全局家规 | `$DSH_HOME/AGENTS.md`（先于项目指令加载） | 同上 |
| 专项流程 | `<cwd>/.dsh/skills/<name>/SKILL.md`（rank 100） | `dsh-skill-filesystem` |
| 技能热更新 | 目录 watch，新增/改名无需重启 | 同上 |
| 数据与记忆 | workspace 里的普通文件 | `tool-fs` 读写 |
| 确定性计算 | 纯 JS 脚本，经 `run_code` 调用 | `@ohos/dsh-ptc-runtime-vm` |

**重要边界**：ACP 的 `session/new` 只有 `cwd` 和 `mcpServers`，**没有 preset / systemPrompt
参数**（已核对 `dsh-acp` 源码）。所以：

- Agent 之间的**能力差异走 skill，不走 preset**；
- preset 是 profile 级的子插件组合，切换要重启运行时（`node::Start` 每进程一次），代价太高；
- 需要"某个 Agent 完全看不到某类工具"时，才考虑多 profile / 多进程，那是后话。

## 4. 卡片系统

### 4.1 卡片的四个必备字段

没有这四个字段的"卡片"只是截图：

| 字段 | 作用 |
|---|---|
| `generatedAt` | 这张卡是什么时候的事实；UI 必须显示"3 小时前" |
| `source` | 哪次会话 / 哪个工具产出的；出错时可回溯 |
| `staleAfter` | 多久算过期；过期要显式提示并可一键刷新 |
| `actions` | 点一下能干什么：继续对话 / 打开另一张卡 / 记录一条 |

### 4.2 七类卡片（覆盖个人场景的绝大多数）

| 类型 | 例子 | 主要原语 |
|---|---|---|
| 状态 | 今日热量、当前体力 | `ring` `metric` |
| 趋势 | 7 日体重、近 10 局胜率 | `chart` |
| 清单 | 今日训练、每日委托 | `checklist` |
| 计时 | 体力回满、下一场活动 | `countdown` |
| 资讯 | 版本公告、循证健康新闻 | `feed`（每条带来源 + 一句"为什么给你看"） |
| 决策 | 审批、二选一 | 复用现有 ApprovalSheet |
| 结果 | 周报、战绩复盘 | `markdown` + `chart` |

### 4.3 原语白名单（v1 十个，够用且可渲染到桌面）

`metric` `ring` `progress` `list` `checklist` `chart(line|bar)` `countdown`
`feed` `markdown` `actions`

规则：

- **未知块跳过并留占位**，不整卡失败（向前兼容）；
- **不做表达式求值**，只做 `{{path}}` 取值，缺失渲染为 `—`；
- 字符串长度、列表条数、图片路径都有上限；
- 卡片里**不放 HTML、不放外链脚本**；需要富交互就走 `actions` 回到对话。

### 4.4 布局与数据分离

这是整套设计里最容易被做错的一步。

```
cards/today.card.json   ← 布局：作者写一次，改它要用户确认
data/today.json         ← 数据：Agent 每次运行覆盖，随便写
```

```json
// cards/today.card.json
{
  "schema": 1,
  "id": "today",
  "title": "今天",
  "staleAfter": 21600,
  "blocks": [
    { "type": "ring", "label": "热量", "value": "{{intake.kcal}}",
      "max": "{{targets.kcal}}", "unit": "kcal" },
    { "type": "metric", "label": "蛋白质", "value": "{{intake.protein}}", "unit": "g" },
    { "type": "list", "bind": "/meals",
      "item": { "title": "{{name}}", "detail": "{{portion}}", "trailing": "{{kcal}} kcal" } },
    { "type": "actions", "items": [
      { "label": "记一餐", "prompt": "帮我记录一餐" },
      { "label": "看周报", "openCard": "week" } ] }
  ]
}
```

```json
// data/today.json
{
  "generatedAt": "2026-10-31T12:40:00+08:00",
  "source": { "session": "…", "tool": "write" },
  "intake": { "kcal": 1240, "protein": 82 },
  "targets": { "kcal": 2000 },
  "meals": [
    { "name": "早餐", "portion": "燕麦 + 鸡蛋", "kcal": 420 },
    { "name": "午餐", "portion": "牛肉面", "kcal": 820 }
  ]
}
```

**为什么分离**：模型每次刷新只写数据，不会把卡片越改越花；用户改布局是显式动作。
否则会出现"昨天的卡和今天的卡长得不一样"这种不可维护的状态。

### 4.5 生产链路：v0 用文件约定，v1 再加插件

| 版本 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **v0** | Agent 用现有 `write` 写 `data/*.json`；App 在 `session.status=idle`、前台恢复、手动下拉时重扫 | **零载荷改动** | 无 schema 校验；刷新有一个事件周期的延迟 |
| **v1** | 新增 `@ohos/dsh-card-publish`（纯 JS，约 300 行）：校验 schema → 原子写 → 经 side-channel 发 `ohos/card.updated` | 一次载荷重打包（约 30 s） | 多一个插件要维护 |

v0 足够验证产品假设；**不要一上来写插件**。

### 4.6 三处渲染的裁剪

| 载体 | 能力 | 刷新 | 限制 |
|---|---|---|---|
| 应用内卡片板 | 全部原语 + 动作 | 事件驱动 | 无 |
| 桌面卡片（Form Kit） | `ring` `metric` `list` `actions` | 系统限制（最快 30 分钟级）+ 打开时刷新 | 不能跑 Node；只读快照 |
| 通知 | 标题 + 一行摘要 + 2 个按钮 | 定时 / 事件 | 无富 UI |

一份 spec 三处渲染的关键是：**桌面和通知只取 spec 的子集，不另写一套内容**。

### 4.7 三种会做歪的卡片（反例）

1. **聊天记录换皮**：把 assistant 的回复塞进卡片。没有状态、刷新无意义，一周后必被删。
2. **一次性 HTML 报表**：好看，但不可上桌面、不可交互、下次刷新就变形。只配当"结果卡"。
3. **一卡一原生页面**：每加一张卡就要发版。这是把可定制性做死。

## 5. 两个样板 Agent

### 5.1 健康教练（饮食 + 健身 + 资讯）

**职责**：把"吃了什么、练了什么、身体怎么变"变成一条不需要意志力的流水线。

```
workspaces/health/
  AGENTS.md                  # 不做诊断；热量下限保护；先估算再确认；数字用脚本
  .dsh/skills/
    log-meal/SKILL.md        # 文字/照片 → 结构化一餐
    plan-week/SKILL.md       # 生成一周训练 + 菜单
    review/SKILL.md          # 周报：趋势 + 依从率 + 下周调整
  scripts/
    tdee.js                  # Mifflin-St Jeor + 活动系数
    macro.js                 # 目标拆分与下限校验
    trend.js                 # 7 日移动平均、依从率
  data/
    profile.json             # 身高体重目标、过敏、忌口
    meals.jsonl              # 追加写，永不重写历史
    workouts.jsonl
    targets.json
  cards/
    today.card.json          # 热量环 + 三餐 + 蛋白 + 记一餐
    week.card.json           # 7 日趋势 + 训练完成率
    plan.card.json           # 本周训练/菜单清单
```

关键设计：

- **一餐一条 jsonl**，卡片是投影。用户手改数据、导出 CSV 都不破坏结构。
- **照片走现有视觉链路**：分享/拍照进 composer → 模型识别份量 → 脚本算营养 →
  写 `meals.jsonl` → 卡片数字变化。识别不确定时，卡片上标"估算"并提供"改份量"。
- **资讯卡必须有来源与理由**：每条 `{title, source, publishedAt, why}`，
  底部"不想看这类"写回 `preferences.json`。没有"为什么给你看"的资讯卡就是 RSS。
- **安全边界写进 AGENTS.md**：不诊断、不推荐极端节食、不做药物建议、
  热量低于下限时拒绝并解释；卡片固定位置放"非医疗建议"。

### 5.2 游戏伙伴

先划清红线：**不做自动操作、不做挂机脚本、不读游戏内存、不做外挂**。
鸿蒙上跨 App 注入需要系统级权限（`NEEDS-ANALYSIS.md` §1.D），普通应用拿不到；
这类需求要明确拒绝，避免合规风险。

能做的，恰好都很适合卡片：

```
workspaces/game/
  AGENTS.md                  # 只谈这个游戏；攻略先查本地 wiki；数值必须脚本算；公告带日期来源
  .dsh/skills/
    patch-notes/SKILL.md     # 抓官方公告 → 结构化（版本/卡池/活动/截止日）
    team-build/SKILL.md      # 配装：先读 roster，再算，再解释
    battle-review/SKILL.md   # 战绩截图 → 复盘
  scripts/
    gacha.js                 # 保底计数、期望抽数、概率区间
    stamina.js               # 回满时间、溢出预警
    damage.js                # 伤害/收益计算
  data/
    roster.json              # 角色/武器/命座
    gacha.jsonl              # 抽卡流水
    stamina.json
    wiki/                    # 用户导入的攻略 md（grep 可检索）
  cards/
    today.card.json          # 每日委托清单 + 体力倒计时 + 卡池剩余时间
    banner.card.json         # 保底进度 + 期望花费
    review.card.json         # 最近战绩：胜率、常用阵容、失误标签
```

四个可落地的能力：

| 能力 | 实现 | 依赖 |
|---|---|---|
| 每日委托 / 体力 | 清单卡 + `countdown` + 本地通知 | 纯本地 |
| 抽卡记录与保底 | 手动/截图录入 → `gacha.jsonl` → `gacha.js` 计算 | 视觉 + 脚本 |
| 版本资讯 | `web_fetch` 官方公告页 → 结构化 → `feed` 卡 | `tool-web` |
| 战绩复盘 | 分享截图进来 → 视觉模型读面板 → 结构化复盘 | 图片链路（已修） |

游戏 Agent 是卡片系统的压力测试：它同时要**定时、计数、外部资讯、图片输入、
确定性计算**——这五样跑通，其他个人 Agent 基本只是换数据和文案。

### 5.3 可行性红黑榜

| 想做 | 判定 | 原因 |
|---|---|---|
| 饮食记录 / 周报 | 绿 | 输入现成（文字/照片/分享），计算确定 |
| 训练计划 / 打卡 | 绿 | 清单 + 通知 |
| 游戏资讯 / 保底 / 计时 | 绿 | 结构化强，天然适合卡片 |
| 健康数据周报（步数/心率/睡眠） | 黄 | Health Kit 需 AGC 申请权限，自签名/开源分发可能拿不到；手动输入保底 |
| 跨 App 自动操作 | 红 | 权限模型不允许 |
| 自动玩游戏 / 挂机 | 红 | 同上，且合规风险 |
| 实时行情 / 高频数据 | 黄 | 无后台常驻，只能打开时拉 |

## 6. 定制的四个层次与边界

| 层 | 改什么 | 谁改 | 成本 | 占比 |
|---|---|---|---|---|
| L1 内容 | 卡片布局、字段、文案 | 用户 / 模型 | 零代码 | ~40% |
| L2 行为 | `SKILL.md`：何时做、按什么步骤做 | 用户 / 模型 | 零代码 | ~35% |
| L3 能力 | 新工具（新数据源、新计算） | 开发者 | 写 JS 插件 + 重打载荷 | ~10% |
| L4 人格 | `AGENTS.md` + 记忆文件 | 用户 | 自然语言 | ~15% |

判断：**90% 的个性化落在 L1/L2/L4，只有 10% 需要 L3。** 所以先把文件约定和渲染器做顺，
把"写插件"留成高级模式；不要一开始做插件市场（鸿蒙上 pnpm 子进程也不可用）。

### 6.1 用户怎么"做一个 Agent"

三条路径，按门槛排序：

1. **模板**：内置 3–5 个（健康、游戏、周报、收件箱、学习），一键创建；
2. **对话生成**：内置 `agent-builder` skill，用户说"做一个跑步 Agent"，
   模型按模板生成 `agent.json` / `AGENTS.md` / 卡片 / 脚本，校验后落盘；
3. **导入**：`.agent.zip`（就是 workspace 去掉会话日志），可分享、可版本管理。

### 6.2 定制化的三条硬边界

- **布局变更要确认，数据更新不要**。否则卡片会在用户眼皮底下变形。
- **Agent 不能改自己的权限档**。权限是用户给的，写进 `agent.json` 但只读展示。
- **跨 Agent 数据默认隔离**。饮食数据不该被游戏 Agent 读到；共享走显式的 `shared/`。

## 7. 路线图

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|

## 8. 与 Muse 对比

> Muse：Meta 2026-09-08 上线的个人 AI Agent（美国先行），云端 `Muse Secure VM` 执行，
> `Sentinel` 监督对外动作，`Muse Spark` 驱动；上线 40 天全球下载约 1090 万，
> 首日留存 73.3%、第 14 天约 22.5%（Sensor Tower / 公开报道）。
> 以下对比只取产品机制，不评价其未公开实现。

| 维度 | Muse | 本仓库 | 判断 |
|---|---|---|---|
| 执行位置 | 云端独立 VM，常驻 | 应用进程内 Node，`--jitless` | 它算力无限、可常驻；我们零数据出域 |
| 触达面 | 跨 App、网页、支付、邮件、日历 | 仅本 App 沙箱 + 分享入口 | **结构性劣势，不追** |
| 主动性 | 可主动联系用户 | 无（计划：提醒代理） | 只能做到"提醒 → 点开" |
| 记忆 | 跨应用云端记忆 | 本地 workspace 文件 | 我们可读、可改、可删、可导出 |
| 审批 | Sentinel + 批准卡片 | ACP permission + ApprovalSheet | 已有；缺"活动记录" |
| 产物 | Artifacts（服务端生成最合适的 UI） | ArtifactDock（文件卡条） | 要补 CardSpec |
| 目标 | Goals（长期目标 + 拆解） | 工具有、UI 无 | 低成本补 |
| 活动 | Activity（后台执行可见） | 仅当前轮 trace | 低成本补 |
| 成本 | 免费 + 交易抽成 | 用户自付 API key | 商业模式不同 |
| 分发 | 商店 + Meta 系导流（95% 用户来自 FB） | 开源 + 侧载 | 冷启动难 |

### 8.1 该抄的三件

1. **Goals**：把"我想开始健身"变成一个持续对象，而不是一张计划表。
   dsh 的 goal 工具已经在，缺的只是一个 GoalBar。
2. **Activity**：后台做了什么必须可见。我们的 `activity.jsonl` 成本极低，
   但它同时是信任基础设施和最好的调试工具。
3. **Artifacts 的思路**：结果用最合适的界面呈现，而不是一段长文本。
   **抄思路，不抄实现**——他们能生成任意 UI 是因为渲染器在服务端；我们必须用受限 DSL，
   才能离线、上桌面、可审计。

### 8.2 不该抄的三件

1. **云 VM 执行**：和"数据不出设备"的叙事直接冲突，也失去离线与零边际成本。
2. **跨 App 操作**：鸿蒙权限模型下拿不到，写进路线图只会制造幻觉。
3. **交易闭环 / 抽成**：那会把产品变成流量分配平台，和"用户拥有的工具"是两种公司。

### 8.3 差异化的三条

- **数据主权**：饮食、健康、游戏记录都在用户自己的目录里，能导出、能 git、能删。
- **Agent 可编程**：用户能改 `AGENTS.md`、加 `SKILL.md`、换卡片布局；
  Muse 的 Agent 是黑箱，只能通过对话影响。
- **零边际成本**：用户自带 key，没有按次计费，也没有"用得多就亏"的激励扭曲。

### 8.4 留存数据给的启示

Muse 首日 73.3%、第 14 天 22.5%——**新奇感消退后，留下的是"每天非它不可的一件事"**。
对我们是同一个问题：如果卡片板不能变成"每天看一眼"的东西，做再多 Agent 也是尝鲜。

所以顺序必须是：**先做"每天会看的一张卡"，再做"很多 Agent"**。
反过来做，会得到一堆没人打开的模板。

## 9. 怎么度量（别只看 DAU）

| 指标 | 说明 | 目标方向 |
|---|---|---|
| 卡片周打开率 | 有卡片的 Agent 中，7 天内被打开过的卡片占比 | ↑ |
| 数据新鲜度 | `now - generatedAt` 的中位数 | ↓ |
| 人工修正率 | 用户手改卡片数据次数 / 生成次数 | ↓（说明算得准） |
| Agent 次周存活 | 创建 7 天后仍被使用的 Agent 占比 | ↑ |
| 桌面卡片曝光→打开 | 桌面卡片点击 / 曝光 | ↑ |
| 每 Agent 日轮次 | 维持一张卡要烧多少模型调用 | ↓（说明脚本承担了计算） |

最后一条尤其重要：**如果每张卡每天都要模型重算一遍，这个产品在手机上不可持续**。
好的卡片是"脚本算数 + 模型偶尔说话"。

## 10. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 卡片变成"漂亮的废话" | 数据不更新，只有壳 | `generatedAt` 必须显示；过期高亮；一键刷新 |
| 模型算错数字 | 热量、保底、配速偏差 | 数字只来自脚本；模型只写文案与解释 |
| 模型改坏布局 | 卡片越刷越花 | 布局与数据分离；布局变更需确认；schema 校验 |
| 多 Agent 记忆串味 | 饮食偏好出现在游戏对话 | workspace 隔离；跨 Agent 共享走显式 `shared/` |
| 包体继续膨胀 | 已 335 MB | 卡片不引入原生依赖；新能力优先纯 JS |
| Health Kit 拿不到权限 | 周报缺数据 | 手动输入保底；权限失败要降级而不是报错 |
| 审核 / 合规 | 医疗建议、游戏外挂 | 免责声明写进卡片；明确拒绝外挂类需求 |
| 通知被用户关掉 | 主动性归零 | 卡片内提示；降级为"打开时 catch-up" |

## 11. 一句话总结

**Muse 把 Agent 做成一个会替你办事的联系人；我们把这个位置让出去，
把它做成一个你能看懂、能改、能带走的看板——卡片是它的状态，对话是它的手。**
